Campfire

An AI onboarding assistant that lives in Slack. Every new hire's questions make the docs a little better for the next one.

2026 · Product, architecture and code by me · Go, React, Claude, MongoDB, Kubernetes

  • I built an AI product from scratch: five Go services, a React admin app, a marketing site and a fake Slack for testing, deployed to Kubernetes with CI/CD.
  • I designed a tool-using Claude agent that runs structured interviews in Slack, turns what people say into a knowledge graph, and writes and maintains Notion pages.
  • Development ran April to July 2026: 280 commits in about 12 weeks, taken to an early-access stage.

The problem

Most of what a new hire needs isn't written down. It's in people's heads and in old Slack threads. Every time someone joins, the team explains the same things again, and the answers disappear once the new hire has them. Onboarding tools track checklists. They don't capture that knowledge.

Campfire tries to capture it. Each onboarding should leave the documentation a bit better than it was before.

How it works

  1. Manager setup. The manager chats with the bot in a Slack DM, whenever they have time. They cover who is joining, who's on the team, which topics matter and who owns each one, and what the first real tasks are. At the end, Campfire sets up a Notion workspace for the new hire.
  2. Team interviews. Campfire interviews each topic owner for about 10 minutes, in Slack, whenever it suits them. It asks about tools, docs, people, common mistakes and recent changes. It follows up on vague answers and reads back what it understood so the owner can confirm it.
  3. Knowledge graph and board. A background pipeline pulls people, tools, systems, processes, decisions and knowledge gaps out of each transcript. It then builds a personal Notion board for the new hire, with a welcome page and tasks to learn, do, watch and meet people about.
  4. New-hire Q&A. The new hire asks questions in Slack. Campfire looks for the answer in the graph, then in linked docs, then in source systems. If none of those have it, Campfire routes the question to the right expert. It records the expert's answer, asks them to approve it, and saves it as a page, so the next hire won't need to ask.

Over time, managers also get an overview of their team's knowledge: gaps in the documentation, questions that keep coming up, and single points of failure, meaning topics only one person knows.

Architecture

Services

  • slack-connector keeps a WebSocket open to Slack's Socket Mode, so the bot needs no public webhook endpoint. It maps each Slack thread to a conversation session.
  • api-server handles about 145 REST routes, runs the Claude agent loop, and schedules interviews and the post-interview jobs.
  • mcp-server is an MCP-style tool server with 76 tools. What the agent may call depends on the session type: a team interview can't use manager-only tools. Each session gets a short-lived signed token that limits it to its own tools.
  • notion-worker syncs Notion in both directions, using a MongoDB-backed job queue and checkpoints. It has versioned migrations for 11+ Notion databases, so board layouts can change without breaking existing workspaces.
  • admin-ui (React + Vite) shows the knowledge graph, interview transcripts, sync state, Claude token usage and agent errors.

The AI layer

  • Router, then specialist. A router prompt sorts every new Slack thread into a type: manager setup, new-hire Q&A, a general issue, or small talk. The thread then goes to a specialist agent with its own prompt and tool set. There are 13 prompts in total.
  • Right model for each job. Claude Sonnet runs the conversations. Claude Haiku handles the cheaper work in the background: pulling facts out of transcripts, summaries and tool sub-calls.
  • Controlled costs. Prompt caching is on for the system prompt and tool definitions. Each turn has a fixed tool budget, and a compact tool catalog lets the model fetch a tool's full schema only when it needs it. Token usage is tracked per customer.
  • Memory without huge contexts. The agent keeps a short saved-context note that it rewrites every turn, plus only the last 10 messages. Long interviews therefore stay cheap and focused.
  • Graph extraction with dedup. Before the analyzer writes anything, it searches the graph for an existing entry. As a result, "the deploy script", "deploy.sh" and "our release tool" end up as one node, not three.
  • Quiet failures. When a tool call fails, the error goes to a private log that shows up in the admin UI. Users in Slack never see raw errors.

Reading files and docs

People don't only talk to Campfire, they also hand it things: a manager drops an onboarding checklist PDF into the setup chat, or an expert shares a link to a Confluence page in the middle of an interview.

  • Files shared in Slack are downloaded and attached to the conversation. Text is extracted from PDF, DOCX, DOC, TXT, Markdown and CSV.
  • The agent reads files through tools. list_files shows what's attached. summarize_file sends the text to Haiku and returns a short summary. The agent can pass a focus ("just the deploy steps"), and summaries are cached, keyed on the file's content hash. get_file returns the full text, and the agent only uses it when it needs exact wording.
  • Linked docs work the same way. find_in_docs searches the connected sources (Notion, Confluence), fetch_linked_doc_summary returns a cached summary, and read_doc pages through the original text.

The pattern is always cheapest first. The expensive Sonnet conversation gets a compact summary, not a 40-page PDF. It goes back to the raw text only when the summary isn't enough.

Key MCP tools

The agent's 76 tools are grouped by job. These are the ones that matter most:

  • Graph: search_graph, get_topic_bundle (a topic plus its neighbours and owner, in one call), get_related, save_graph_observations, link_entities
  • Files and docs: list_files, summarize_file, get_file, find_in_docs, fetch_linked_doc_summary, read_doc, check_doc
  • Onboarding flow: setup_team, save_topic, schedule_interviews, finalize_setup, end_interview
  • Q&A and gaps: create_knowledge_gap, start_question_thread (pulls the right expert into a thread), record_answer_feedback
  • Notion pages: write_page, patch_page, edit_page, summarize_page, plus a set of tools for the new hire's dashboard
  • Memory: get_context, save_context

The knowledge graph

Everything Campfire learns is stored as nodes and edges. Node types:

  • People and structure: people, roles, companies
  • What the team works with: tools, systems, processes, projects, features, concepts
  • Onboarding: topics, tasks, interviews, documents
  • What's missing: knowledge gaps (with where they came from, a confidence score and how they were resolved), questions new hires asked, and feedback

Edges connect them with 25+ typed relationships. Some examples: Anna owns Deployments, Deployments uses_tool ArgoCD, Ben contact_for Billing, Releases documented_in the release guide, the release guide contradicts what Ben said in his interview, and the new hire struggled_with local setup. This is what lets Campfire answer "who do I ask about X?", notice when a doc is out of date, and find topics only one person knows.

Data

MongoDB is the source of truth. Every document has an organization ID, so one deployment serves many companies. Graph nodes live in one collection per type. The relationship types (owns, uses_tool, contact_for, blocks, and so on) live in a separate edges collection with an index on each end. This makes traversal fast in both directions, and merging two duplicate nodes only means rewriting their edges. Redis is used for caching. Uploaded files go to Cloudflare R2, and text is extracted from PDFs and DOCX files so they can be searched.

Testing: a fake Slack

Testing a Slack bot against real Slack is slow and hard to repeat, so I built fake-slack, a TypeScript service that imitates Slack's Web API, Socket Mode and OAuth. It has a UI that can run several workspaces, and scripted AI personas can play the manager, the team members and the new hire. This let me run full onboarding cycles end to end, locally and in CI, without a real Slack workspace.

Infrastructure

Everything runs on Kubernetes, with Kustomize overlays for the dev, qa and prod environments. Traffic comes in through a Cloudflare Tunnel, so the cluster has no open ports. Security details:

  • Slack and Notion connect over OAuth, and their tokens are encrypted at rest with AES-256.
  • Admins sign in with JWT sessions.

GitHub Actions builds seven container images and deploys every push to the dev environment automatically. Promotion to qa and prod is manual. For local development, a single docker-compose file starts the whole stack.

What I learned

The hard part was not getting the model to talk. It was building everything around it:

  • deciding which tools each kind of conversation may use
  • keeping extracted knowledge free of duplicates
  • keeping costs predictable
  • failing quietly
  • testing the whole thing end to end
