FlowGeo

Tracks what ChatGPT, Claude and Gemini say about your brand: who they recommend, in what order, and which sources they cite.

2025–2026 · Offline · Built with Or Druker · Backend, AI pipeline and infrastructure by me · Go, Python, React, MongoDB, NATS JetStream, Kubernetes

  • A two-person product, built with Or Druker. I designed and built the backend: six Go services, the Python LLM service, the event schemas and the Kubernetes/GitOps setup. I also wrote a large part of the React dashboard. Or started the project, built the first version of the React app and many of its pages, and made the marketing site.
  • The core is an event-driven AI pipeline. It writes prompts and buyer personas, runs them against three model providers, and pulls brand mentions, rankings, sentiment and cited sources out of every answer. Then it cleans up after itself: it merges duplicate companies and retires prompts that never surface a brand.

The problem

More and more people ask a chatbot instead of a search engine: "What's the best CRM for a small agency?" The answer names a few products and skips the rest. A company has no easy way to see whether it shows up, how high it ranks against its competitors, or which web pages the model relied on.

This field is called GEO, generative engine optimization. FlowGeo measures it. It asks the models the questions real buyers ask, many times and in many variations, and turns the answers into numbers a marketing team can follow over time.

How it works

  1. Onboarding. A customer (a "partner" in the code) enters their company name. The LLM service looks the company up on the web and suggests up to 10 of its products. The customer picks one, and FlowGeo creates a visibility metric for it with generated prompts, competitors and locales.
  2. Prompts and personas. Prompts are written the way a buyer would ask them. Each prompt has variants per language and location. A second metric type, persona_visibility, rewrites every prompt in the voice of a generated buyer persona and sends the persona's description along with it. This shows whether the answer changes depending on who is asking.
  3. Scheduled runs. The scheduler checks every 10 minutes which metrics are due (daily, weekly or monthly). For each due metric it creates one task per prompt variant and model, and publishes the tasks as events.
  4. Answers. The LLM service asks each question to ChatGPT, Claude or Gemini, with web search turned on for ChatGPT, and publishes the answer text.
  5. Extraction. The post-processor sends every answer back to the LLM service for structured extraction. It gets back each brand mention, with its exact position in the text, the company and product, a rank and a 1–5 sentiment score, plus the sources the answer cited. Then it matches each name to a known company or product, or creates a new competitor.
  6. Cleanup. After a run, a chain of post-processing steps merges duplicate companies and products, scores how relevant each competitor is, retires prompts that produced no mentions, generates new prompts to replace them, and extracts the attributes the models associated with each brand.
  7. Dashboard. The analytics API turns all of this into share of voice over time, rankings, sentiment, cited sources and prompt-level detail. Users can filter by model, persona and attribute.

A separate website audit checks whether the customer's own site is easy for AI crawlers to read. When a run finishes, the customer gets an email.

Architecture

Services

  • client-api (Go) has 88 operations, all generated from an OpenAPI spec with oapi-codegen. It handles partners, products, competitors, personas, prompts, metrics, users and onboarding. It also handles login: one-time links by email via Mailjet, or OAuth with Google, Apple, GitHub or Facebook, followed by a JWT in a cookie. Admins and agencies can switch between partners.
  • analytics-api (Go) serves the dashboard: share of voice, overall and per time bucket, product rankings, mentions, cited sources, prompt quality and insights.
  • scheduler (Go) decides when metrics run and turns them into tasks. It also watches running executions: a task times out after 10 minutes, an execution after 12 hours and post-processing after 30 minutes. Admins can stop or restart a run by hand.
  • llm (Python, FastAPI) answers questions from JetStream and exposes about 20 HTTP endpoints for generation and extraction, such as /generate-questions, /adapt-questions-to-personas, /extract-answer-insights and /extract-merge-candidates.
  • post-processor (Go) turns raw answers into structured data and runs the cleanup chain after each execution.
  • website-audit (Go) runs 15 checks on a customer's website.
  • cost-tracker (Go) reads llm.usage events and calculates the cost of each call from a per-model price table. The admin dashboard shows the totals.

Shared Go code lives in services/go: auth, JetStream, MongoDB, caching, logging and a typed HTTP client for the LLM service (llmconnector). Event and database types live in schemas/ and are used by every Go service.

The AI layer

  • Three providers, one interface. LLMEngine.answer_question routes each task to OpenAI, Anthropic or Google. A mapping file resolves generic names like CHAT_GPT or CLAUDE_SONNET to concrete model versions, so changing a model doesn't need a code change. New onboarding metrics use ChatGPT and Claude by default.
  • Named profiles for every job. The 19 internal LLM jobs (generate personas, translate prompts, extract insights, classify a company or product, find key pages, and so on) each have a profile with a model and a reasoning effort. Most run on gpt-5-mini. Five use gpt-5.1.
  • An adaptive rate limiter per provider. Each provider has its own requests-per-minute limit (59 for OpenAI, 29 for Anthropic, 5 for Gemini). When a provider returns a rate-limit error, the limiter pauses for the time the provider asked for and cuts throughput by 20%. After 8 successful calls in a row it adds one request per minute back.
  • New users go first. Onboarding jobs, like generating personas and prompts or extracting products, are marked high priority. They skip ahead of background extraction, so a new customer isn't stuck waiting behind a big scheduled run.
  • Prompts that tell the model how to rank. The extraction prompt gives exact rules. Rank comes from list order or from explicit preference. Entities in the same list item share a rank. Ranks must be consecutive from 1, or they're left out. Sentiment defaults to 3 when unclear.

Turning answers into clean data

Most of the hard work happens after the model has answered. Model output is messy, and the dashboard is only as good as the matching behind it.

  • Mentions must exist in the text. The extractor returns character offsets for each mention. If the offsets are wrong, findMentionSpanFromContext searches the answer for the surface text, the product name or the company name, with an exact, case-insensitive and then flexible match. Mentions that can't be found are dropped.
  • Name resolution with a shared cache. Deciding whether "Acme Cloud" is a company, a product or noise takes an LLM call. Results are cached in Redis per partner and name for 24 hours. A short "pending" key stops two workers from classifying the same name at the same time.
  • Back-pressure. The post-processor processes at most 5 answers per partner and 100 overall at a time. A watchdog frees slots that get stuck, so one large customer can't block everyone else.
  • Resumable cleanup. The post-processing chain has seven steps: merge companies, merge partner products, score relevance, deactivate low-relevance competitors, check prompt quality, generate new prompts, extract attributes. Each step's state is saved on the execution, so a restart skips the steps that already finished.
  • Prompts that improve themselves. If a prompt was answered but no answer mentioned any brand, it is switched off with the reason deactivated by system. New prompts are then generated to keep the metric at its target size.
  • Regression tests from real data. A script exports extraction cases from the database into fixtures. The post-processor's test suite runs against them, so changes to the matching logic can be checked against real answers.

Website audit

The audit fetches the customer's site the way an AI crawler would, including with a GPTBot user agent. Its 15 checks cover reachability, robots.txt rules for AI bots, llms.txt, Markdown versions of pages, structured data, canonical tags and indexability, JavaScript rendering risk, readability, duplicate pages, broken internal links, caching headers and freshness. Two checks use the LLM: one finds the site's key pages and one checks whether their content is complete.

Data and events

MongoDB holds everything: partners, products, competitors, personas, metrics with their prompts and variants, executions with their tasks, answers, mentions, sources, rankings, LLM usage and audits. Services talk through 17 JetStream topics, such as metric.execution.question, metric.execution.answer, metric.manifest.post.process and llm.usage. Every event has a typed schema in schemas/events. A run is tracked as a manifest of task IDs. When every task has reported back, the scheduler starts post-processing.

Infrastructure

The whole system runs on Kubernetes from one Helm chart, with dev, qa and prod environments. Flux applies each environment from Git. Secrets are stored in Git only in encrypted form, as Sealed Secrets. Traffic comes in through a Cloudflare Tunnel to a Traefik ingress with a rate-limit middleware. JetStream runs as a StatefulSet on a persistent volume. Logs are collected by Fluent Bit and shown in Grafana, with Loki storing them.

Every push to main triggers GitHub Actions to build nine container images, push them to GHCR, and commit the new image tags to the dev values file. Flux then deploys them. A manual workflow promotes the dev images to qa or prod. For local work, one docker compose --profile local command starts the full stack.
