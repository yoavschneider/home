RepoGuide

Coding agents start every task from zero. RepoGuide learns from past agent sessions in a repo and gives the next agent a short briefing before it starts searching.

2026 · Public beta · Product, architecture and code by me · Go, React, Claude, MCP, MongoDB, Kubernetes · repoguide.dev · GitHub

  • I built a developer tool on my own: a Go CLI with a built-in MCP server, a Go backend, a React web app, a shared Go module and a benchmark harness. That's about 69,000 lines of Go. The CLI ships through Homebrew, signed and notarized for macOS.
  • The core is a mostly deterministic retrieval pipeline. It parses session logs from seven coding agents, mines which files get read and edited together, and builds an evidence-backed briefing for the current task. Claude only routes the task and picks from candidate IDs. It never writes the advice.
  • I measured it with a reproducible benchmark (108 agent runs): 32% fewer input tokens on average with the same 94% success rate, but only 4% lower cost. About 300 commits between July and August 2026.

The problem

A coding agent like Claude Code or Codex knows nothing about your repo when a task starts. It greps, opens files, guesses, opens more files, and only then makes its first edit. The next session does the same search again, even when yesterday's session already found the right files, hit the same dead end and learned which test catches the bug.

The usual fixes don't solve this. Code search tells the agent where code is, not which files mattered for this kind of change. RAG finds text that looks similar. A CLAUDE.md file is what someone wrote once, and it goes stale.

RepoGuide uses a different source: the agent sessions themselves. They record what was searched, read, edited and tested, and what failed. That is evidence of what actually worked in this repo.

How it works

  1. Setup. repoguide setup finds the Git repos on the machine, initializes one, and registers the RepoGuide MCP server in every coding agent it detects: Claude Code, Codex, Cursor, OpenCode, GitHub Copilot and Gemini CLI. Cloud mode signs in to the hosted backend. --offline runs everything locally.
  2. Ingest. The CLI reads the agents' own session logs from disk and turns them into one common event stream: prompts, file reads, edits, searches, shell commands, test runs and token usage. Secrets are redacted. Prompts can be redacted too before anything leaves the machine.
  3. Analyze. The analysis step finds files that are read and edited together, which tests belong to which code, and which searches led nowhere. It groups the files into subsystems, and Claude Sonnet turns those groups into named topics (for example "checkout" or "order refunds"), each with start files, workflows, risks and tests.
  4. Brief. When a new task starts, the agent calls repoguide_get_repo_experience with the task. RepoGuide matches it to a topic, finds the past sessions that did similar work, and returns a compact package: where to start, what to avoid, which files usually change together, and how to validate the change.
  5. Feedback. At the end of the session, a hook nudges the agent to call repoguide_record_feedback: which advice helped, which was wrong, what was missing. Feedback moves each advice item's confidence up or down and can patch topics, so the experience improves with use instead of going stale.

Architecture

Components

  • repoguide CLI (Go, Cobra, Bubble Tea) is what users install. It discovers repos, parses session logs, installs the MCP server and hooks, and runs the MCP server itself. In offline mode it also runs the whole analysis locally on pure-Go SQLite, with Claude reached through the claude, codex or gemini CLI the user is already logged into, or through an ANTHROPIC_API_KEY.
  • backend (Go, standard net/http, about 65 routes) receives zipped session events, runs the analysis and the topic generation, answers MCP calls for cloud repos, and processes feedback in a job queue that resumes after restarts. It also handles teams, plans and limits, and an admin console.
  • Web app (React, Vite, Tailwind) is the marketing site, the benchmark page and the dashboard. Users can browse their repos, sessions and topics, and edit or disable a topic entry by hand. Every entry keeps its provenance, so a human edit is recorded as one.
  • repoguide-core is a small shared Go module with the domain models, the API contracts between CLI and backend, and the briefing builder. Both runtimes use the same code, so offline and cloud give the same answer for the same data.

Reading seven agents' session logs

Every agent stores its history in its own format. RepoGuide has parsers for Claude Code, Codex, Cursor, Gemini CLI, GitHub Copilot CLI, Copilot in VS Code and OpenCode (including its SQLite store). Each parser maps tool calls to the same event types: a prompt, a read with its paths, a write, a search with its query, a shell command with its exit status. It also picks up the agents' own memory files for the repo, such as Claude's project memory and Codex memories.

Paths are normalized to the repo root, including repos nested inside a workspace. Before upload, sanitizeEventLogForUpload runs secret redaction over every text field, and with the privacy setting off it replaces prompts with [redacted prompt]. RepoGuide never uploads the repository itself.

From sessions to topics

The analysis (BuildRepoAnalysis) is plain counting, no model involved. For every pair of files it counts the sessions where they were read together, edited together, read one before editing the other, or touched in the same prompt. Each signal has a weight: co-edit 5, read-before-edit 4, same prompt 3, co-read 2, same session 0.5. The weighted count is divided by sqrt(sessions(A) × sessions(B)), so two files that are open in every session don't look related just because they're popular. Weak pairs are dropped. The rest form a graph whose connected components are split into groups of at most 12 files.

The same pass collects test signals (which test files and commands follow edits to which code), search discoverability (queries that led to a read, and queries that went nowhere) and repeated detours. Claude Sonnet then gets the candidate groups, with their prompts, commands and tests, and names them as topics. If the model call fails, a deterministic fallback still produces topics.

Building the briefing

The briefing for one task comes from BuildTaskPackage in the shared module:

  • Find similar sessions. Each past session that edited something is scored by its single best-matching prompt against the task, using token overlap divided by sqrt(|task| × |prompt|), after stop words, stemming and a few synonym groups. It also has to touch the topic's files. The threshold is 0.30, and at most 20 sessions are kept.
  • Aggregate what they did. A file counts as typical if at least half the matching sessions edited it. The order in which sessions edited files gives a workflow ("A and B are commonly edited together, 3/4 sessions"). Topic files that similar sessions rarely touched become "avoid" hints. Test commands that were actually run become validation advice. Commands that failed are not turned into advice.
  • Be honest about thin evidence. Workflows and scope advice need at least two matching sessions. With fewer than three, the briefing says the pattern is tentative. With none, it falls back to the topic's curated guidance and labels it as such.
  • Keep it small. A normal task gets at most 6 items and 2,400 characters. A cross-cutting task gets 9 items and 3,200 characters.

Every advice item carries its evidence: the IDs of the sessions that support it, the support count and the population.

The model picks, it doesn't write

Claude Haiku is used twice per briefing, and both times its job is narrow.

  • Topic routing (SelectTopic) matches the task to a topic, with a calibrated confidence. Past feedback adds positive and negative routing examples. A task with fewer than three distinct words, or no strong match, gets a clarifying question and a list of candidate topics instead of a guess.
  • Advice selection (SelectAdvice) gets the candidate items and returns only their IDs, grouped by category. The system prompt says it is "an evidence selector, not an advice author". The code enforces this: unknown IDs, wrong categories, duplicates and anything over budget are dropped. The JSON decoder rejects unknown fields. A start file is always kept. If the call fails, a deterministic selection is used.

The advice text comes only from session history or curated topic data. The model can't invent a file path or a step.

The feedback loop

Feedback names helpful and unhelpful advice by stable ID, and adds free text about what was wrong or missing. Each item's confidence is a smoothed ratio: its session support acts as a prior with weight total + 2, and each helpful or unhelpful rating adds one observation. One bad rating can't wipe out an item backed by ten sessions, but repeated complaints will. Topic routing confidence moves the same way, by small steps. A 4–5 star rating closes 8% of the gap to 0.95, a 1–3 star rating 10% of the gap to 0.05.

Feedback is also classified by Haiku into actionable items. Then a patch job has Sonnet propose edits to the topic, or a new topic. An agent can propose one reusable "candidate rule" per session, but the rule only becomes guidance once later sessions or a developer back it up.

Keeping file paths current

Experience is useless if it points at a file that was moved last week. The CLI reads the repo's rename history (git log --find-renames=90% --diff-filter=R) and maps old paths to new ones. On every MCP call it also sends the list of files that exist on the repo's configured branch, and every path in the topic and the briefing is filtered against it.

That filter caused a bug once. Older CLIs didn't list files inside Git submodules, so filtering would have deleted every submodule path. The backend now reads the CLI version from a request header and skips the filter for clients that are too old. Skipping the filter makes the briefing a bit worse. Filtering with an incomplete list would make it wrong.

How agents use it

The CLI is its own MCP server. It speaks JSON-RPC over stdio, written by hand without an SDK, and exposes six tools:

  • repoguide_get_repo_experience: the main entry point. Task in, topic match and compact briefing out.
  • repoguide_list_topics: candidate topics, for when the match is ambiguous.
  • repoguide_get_test_context: which tests to start with for a topic.
  • repoguide_get_search_context: reliable queries, ambiguous ones to avoid, and files that are hard to find by search.
  • repoguide_get_full_topic_context: the full topic, only when the compact one isn't enough.
  • repoguide_record_feedback: end-of-task feedback, with structured advice evaluation.

Agents only use a tool when they're told to. In Claude Code, a UserPromptSubmit hook suggests repoguide_get_repo_experience on the first prompt of a session. A Stop hook nudges for feedback once, only if the session actually used RepoGuide. By default the hook asks the user before sending feedback, because feedback sends task metadata. Codex gets the same Stop hook, and Gemini CLI gets equivalent hooks. Where hooks aren't used, an instruction block in CLAUDE.md or AGENTS.md does the same job. Managed pre-commit and post-commit hooks strip that block from the index and mark the file --skip-worktree, so it never ends up in a commit or in git status.

Measuring it on real repos

Comparing sessions that used RepoGuide against sessions that didn't is misleading, because agents choose to call the tool more often on some kinds of task than on others. So the MCP server holds back the briefing in 20% of sessions by default. The choice comes from a SHA-256 hash of the session ID, so every call in one session gets the same answer. Held-back responses carry a marker that the session parser recognizes later. repoguide stats then compares the two groups by agent and by change size.

There is also a free local report (curl -fsSL https://repoguide.dev/report.sh | sh). It downloads a checksum-verified binary to a temporary folder and shows, for the user's own past sessions, how many files, searches, tool calls and tokens agents spent before their first edit. Nothing is uploaded.

The benchmark

repoguide-benchmark is a Python harness (standard library only) that runs locally, in Docker or as a Kubernetes Job. The method:

  • Build. An agent builds RoastCart, a small coffee-shop app (Go backend, React shop, React admin), through 42 small developer tasks. RepoGuide learns from exactly those sessions. The repo is snapshotted, so every later run starts from byte-identical state.
  • Evaluate. 18 test tasks extend the subsystems the warmup built, for example "add q and category filters to the product listing API, following the admin order filter's conventions". Each task runs 3 times with RepoGuide and 3 times without it, each time on a fresh copy of the snapshot, with Claude Sonnet 5.
  • Grade. Only mechanical checks, no LLM judge: the repo's test suites pass, the diff touches the right apps and matches task-specific patterns, and tests were added. A run where the RepoGuide arm never called the tool is marked invalid. The feedback tool is blocked during evaluation, so one test run can't teach the next.

Results from the published run on 17 July 2026 (54 runs per arm, none invalid):

  • Input tokens: 16,222 → 11,041 on average, 32% fewer. The best task saved 70%. Five of the 18 tasks used 2–10% more.
  • Success rate: 94% in both arms (51 of 54). RepoGuide made the agent cheaper to run, not more correct.
  • Navigation: tool calls 46.9 → 41.4, searches 7.4 → 5.0, files read before the first edit 7.9 → 7.4.
  • Cost: $1.45 → $1.39 per task, only 4% cheaper. Wall time was the same, 233 seconds.

The cost result is the important caveat. Uncached input is only about 3% of a run's cost, and cache reads and output make up most of the bill, so a 32% cut in input tokens barely moves the price. The variance is also high: the standard deviation of input tokens is nearly as large as the mean, with only 3 repetitions per task, one model and one small, agent-built repo. The harness also has a second mode on a pinned Home Assistant checkout with fictional integrations, built to test a large real codebase, but I haven't published results from it.

Infrastructure

The cloud runs on a k3s cluster managed with Flux. The backend and web app are Kubernetes deployments, and MongoDB is a shared replica set in the same cluster. Traffic comes in through a Cloudflare Tunnel, and Traefik routes /api/ to the backend and everything else to the web app. Certificates come from Let's Encrypt.

  • Deploys: pushing a vX.Y.Z tag makes GitHub Actions build both images, push them to GHCR, and commit the new tags into the Kubernetes manifests. Flux then applies that commit to the cluster. Nothing is deployed by hand.
  • CLI releases: bumping a VERSION file tags the commit and runs GoReleaser. It builds macOS, Linux and Windows binaries without cgo, code-signs and notarizes the macOS builds, publishes them with checksums, and updates the Homebrew cask.
  • Auth: the web app uses GitHub, GitLab and Google OAuth or email and password, with JWT sessions. The CLI signs in with a device-code flow. The CLI only talks to an allow-listed backend host and request paths.
  • Other: transactional email goes through Cloudflare Email Sending. Secrets live in Kubernetes Secrets, never in the repos. For local development, one docker-compose file starts MongoDB, the backend and the web app.
