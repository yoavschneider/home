VHS Dreams

A beat-synced music video editor. Upload a song and some footage, and it cuts the video to the music and gives it an analog VHS look.

2026 · Offline · Product, architecture and code by me · Go, Python, Next.js, FFmpeg, MongoDB, Redis, Kubernetes

Note: VHS Dreams is offline. This page describes the code as of its last commit in July 2026.

  • I built a full media product on my own in about five weeks: a Go API, a Python media worker and a Next.js editor, with Stripe payments, deployed to Kubernetes with CI/CD.
  • The hard part was making cuts land on the beat. Off-the-shelf beat tracking drifted over a long track, so I use it only to find the first downbeat and then build an exact tempo grid from there. Cut points come from bar intensity and kick and frequency peaks, and a scoring function matches each cut to a scene by its visual features.
  • Rendering runs as a queue of small jobs with heartbeats and recovery, so a crashed worker doesn't lose work. Exports encode in batches, add audio-driven effects, and run the same ntsc-rs analog filter that the browser previews through WebAssembly.

The problem

Cutting a music video by hand is slow. You find the beats, pick a clip for every bar, trim it to length, and repeat that a few hundred times for one song. Most of that work is mechanical. The song already says where the cuts should go, and the footage already says which shots are calm and which are busy.

VHS Dreams does that mechanical part. It reads the song's tempo, bars and energy, splits the footage into short scenes, and builds a first cut. The user then edits that cut in a grid, picks an analog look, and exports an MP4.

How it works

  1. Add a song. The user creates a project and uploads an audio file. The browser sends it straight to object storage with a presigned URL. The worker converts it to a standard WAV and then runs a chain of analysis jobs: tempo, the beat and bar grid, per-bar features and song parts, and kick and frequency-band peaks.
  2. Add footage. The user uploads videos from a computer, or from a phone by scanning a QR code. They can also search Internet Archive, NASA and Wikimedia Commons for public-domain clips from inside the studio. Each video goes through a 14-step pipeline that finds scene cuts, scores each scene, and keeps up to 12 short clips with thumbnails.
  3. Auto-cut. When the audio analysis finishes, the project is cut automatically. Quiet bars become long tiles, intense bars get split on kicks and peaks, and every tile gets a scene whose visual features fit that moment in the song.
  4. Edit. The editor shows the song as a waveform with lanes for bars, beats and peaks, and the cut as a grid of tiles under it. The user can split, merge and drag tiles, swap scenes, set speed or reverse, and preview the whole thing in the browser with the analog filter on.
  5. Export. The user picks a quality (360p, 720p or 1080p), an analog preset and an effects set. The worker renders the MP4 and stores it, and the user downloads it from the project page.

Architecture

Components

  • api (Go, standard net/http, about 70 routes) owns users, projects, songs, videos, scenes, tiles, exports and plans. It creates jobs, enforces plan limits, builds the auto-cut, handles Stripe Checkout and its webhook, and runs a background cleanup that deletes expired exports and libraries.
  • worker (Python 3.12) does all media work: audio analysis with librosa and SciPy, scene detection with PySceneDetect and OpenCV, and rendering with FFmpeg and ntsc-rs. It pulls jobs from Redis and runs export, video and audio jobs in separate thread pools, so a long export can't block a short audio job.
  • web (Next.js 15, React 19) is the landing page, pricing and legal pages, the studio dashboard, the video library, and the editor. The editor uses WaveSurfer.js for the waveform and dnd-kit for dragging tiles.
  • MongoDB holds durable state: users, projects, audio and video assets, scenes, tiles and job history. Redis holds the job queue, live job status and worker heartbeats. Cloudflare R2 stores media.

Finding the beat grid

Everything depends on the bar grid. If it is a little off, every cut feels late. I had two problems to solve.

  • Tempo octave errors. Beat trackers often report half or double the real tempo. The worker collects candidates from several estimates (librosa's tracker, the median and mean of per-frame tempo, and the top three histogram bins), adds the half and double of each, and scores every candidate. The score combines autocorrelation at that tempo, how strong the onsets are on the beats, and how much stronger they are on the beats than between them. A small bonus goes to tempos between 70 and 180 BPM. The user can override the result.
  • Drift. librosa's beat tracker drifted out of line in the second half of some tracks. So the worker uses it only to find where the music starts and where the first downbeat is. For the downbeat, it tries all four phase offsets and picks the one with the strongest onsets on beat one. From there it builds a perfectly even grid at the chosen tempo. Pickup beats before the first downbeat are kept.

Each bar then gets features: loudness (RMS), onset density, spectral flux, bass energy and brightness. They are normalized across the song and combined into an intensity score (0.35·RMS + 0.25·onsets + 0.20·flux + 0.20·bass) with a label from low to peak. SciPy's find_peaks marks peak bars and sudden rises, which the editor shows as drops. A separate job finds kick drums in the 40–120 Hz band with an adaptive threshold, plus peaks in four frequency bands.

Picking scenes from footage

A video goes through 14 small jobs, from import to finalize. Each job does one step, saves its result and queues the next one. The interesting steps:

  • Detect. PySceneDetect looks for cuts. If it finds too few usable scenes, it retries with lower thresholds (5, 3, 2, 1.5). A video with no cuts at all becomes one scene.
  • Filter. Scenes under 1.5 seconds are dropped. Scenes over 30 seconds are split into chunks.
  • Score. Each scene gets motion (Farneback optical flow), brightness, contrast, colorfulness, sharpness (Laplacian variance) and a frame-difference movement score. To keep this fast, all sample timestamps are sorted so one video reader only seeks forward, and frames are downscaled to 320×180 when read.
  • Select. Scenes are ranked by 0.45·motion + 0.20·contrast + 0.20·colorfulness + 0.15·sharpness. The top 12 are picked greedily, skipping any scene that starts within 3 seconds of one already picked or whose histogram looks too similar. That keeps the library varied instead of 12 shots of the same moment.

The selected scenes are cut into short H.264 clips with thumbnails and saved as scene documents.

The auto-cut

The auto-cut runs in the Go API in two steps. When the audio analysis is done, the worker calls the API with a short-lived signed token.

  • Where to cut. Bars below 0.3 intensity are merged up to four at a time, and bars below 0.55 up to two. A drop bar gets one long tile across two bars. Bars at 0.42 or above are split into up to five cuts. Cut candidates are beats and the kick or band peaks the user chose, and peaks score higher than plain beats. Cuts must be at least a quarter bar apart. A fixed pattern based on the bar number adds or removes a cut now and then, so bars with the same intensity don't all get the same rhythm.
  • Which scene. Each tile gets metrics: intensity, length, position in the song, momentum (the change from the previous tile) and four frequency bands. A mapping pairs each tile metric with a scene metric, for example "intensity ↔ motion", with a weight. A scene's score is how closely it matches across all pairs. Scenes lose points for being used often and for looking like the previous tile, and a small random term keeps re-runs different. The default mapping is shuffled, so "auto-assign" gives a new take every time.
  • Fit. If a clip is shorter than its tile, it plays at half speed or loops. Some tiles randomly get double speed or reverse. When one scene fills several tiles in a row, every second one plays reversed.

Rendering the export

  • Batches. A song can have hundreds of tiles. One FFmpeg filter_complex with all of them would open too many files at once, so tiles are encoded in batches of 50. The batches are joined with the concat demuxer without re-encoding, and the song is mixed in at the end. Clip audio is dropped.
  • Effects. There are 18 effects, such as punch zoom, camera shake, RGB split, glitch blocks, film grain and scan lines. Each one is tied to an audio feature: zooms follow bass energy, glitches follow onset density. Their strength scales with that feature in the tile's bar, from 40% in silence to 100% at full level. Every tile gets one grain or color effect as a base, and at most three effects in total. Effects are applied inside the same encode, not in a second pass.
  • Analog look. The six presets (VHS, S-VHS, Betamax, composite, broadcast, heavy) are settings files for ntsc-rs, an open-source NTSC and VHS simulator. The worker image builds it from source in a Rust build stage. An intensity slider scales the numeric settings linearly. If ntsc-rs fails, a pure-FFmpeg filter chain gives a similar look.
  • Preview. The editor runs ntsc-rs compiled to WebAssembly on a canvas, frame by frame, so the preview shows roughly what the export will look like.
  • Quality. Preview is 640×360, SD is 1280×720 and HD is 1920×1080, all at 25 fps. Exports over 64 MB are uploaded to R2 in parts.

A job queue that survives crashes

Media jobs take minutes, and workers get restarted. The queue is a Redis list, and every job also has a document in MongoDB.

  • Claiming. A worker claims a job by updating its MongoDB document from queued. If the document is gone, for example because the user deleted the video mid-import, the job is dropped.
  • Heartbeats. Each worker writes a heartbeat to Redis every 60 seconds. Every 30 seconds, workers look for running jobs whose worker has been silent for 150 seconds and put them back in the queue. A second check, which reads only MongoDB, covers the case where Redis lost the job-to-worker map.
  • Stalled jobs. A job that is "queued" in MongoDB but missing from Redis is re-queued, at most three times. After that it fails with a clear error instead of looping.
  • Ordering. Follow-up jobs go to the front of the queue and new jobs to the back, so pipelines that already started finish before new ones begin.
  • Fair exports. If a user already has as many exports running as their plan allows, the worker puts the job back in the queue with a "waiting for a slot" message. Other users' exports keep running.

Plans and limits

There are three plans: Free, a Day Pass and a Week pass, bought through Stripe Checkout. Plans differ in exports per day or week, parallel exports, maximum video length (10 or 30 minutes), scene library size and how long files are kept. The API checks the limits before it queues anything. An export that is too long is trimmed and marked as trimmed, not refused. A background job deletes expired exports and libraries and moves expired passes back to Free.

Problems in production

  • Upload size. Cloudflare caps request bodies at 100 MB, so large uploads failed. Songs now go straight from the browser to R2 with a presigned PUT, with a normal upload as fallback.
  • Exports taking the site down. FFmpeg used every core it could get. I capped it at four threads and added CPU and memory limits to the pods. The workers also run on their own node.
  • YouTube import. I first imported footage from YouTube, then removed it and switched to public-domain archives, which have no licensing issues.
  • Duplicate imports. Double clicks started the same import twice. The API now ignores an import whose source is already queued for that user, and caps each user at 10 imports at a time.

Infrastructure

Everything runs in one Kubernetes namespace. The API, web app, worker, MongoDB 7 and Redis 7 are deployments, and MongoDB and Redis keep their data on persistent volumes. Two worker replicas run on a separate node and share a cache folder, so a source video is downloaded once and reused by later jobs.

  • Ingress: a cloudflared pod connects to a Cloudflare Tunnel, so the cluster has no public ports. The tunnel can't rewrite paths, so a small nginx proxy strips the /api prefix before requests reach the Go API.
  • Deploys: every push to main makes GitHub Actions build the three images for arm64 on an arm runner and push them to GHCR. The next job applies the manifests, sets the new image tags and waits for the rollouts.
  • Security: email and password or Google sign-in, with JWT sessions. Cloudflare Turnstile protects sign-up and login. Secrets live in Kubernetes Secrets.
  • Local development: one docker-compose file starts the whole stack with local file storage instead of R2. Worker tests run inside the worker's Docker image.
